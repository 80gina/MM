# Mindily 팀 프로젝트: 초보자용 실행 순서

## 0. 이번 1차 결과물

현재 버전은 사용자 경험을 먼저 검증하는 프론트엔드 MVP다. 일기 작성부터 감정 확인, 사용자 수정, 힐링 활동, 기록 확인까지 전체 흐름을 한 번에 시연할 수 있다. 감정 분석은 아직 키워드 기반 데모이며 실제 KcELECTRA API로 바꿀 수 있도록 화면 데이터 구조를 분리했다.

## 1. 과제 요구사항과 우리 범위

- 생성형 AI/AI Agent가 핵심인 서비스
- 필수 기술 2개 이상: `RAG + Long-term Memory`를 핵심으로 사용
- 별도 분류 모델: AI Hub 감정 데이터로 파인튜닝된 공개 KcELECTRA 활용
- 실제 배포, 사용자 5명 이상 테스트, 피드백 반영
- GitHub 버전 관리, README, 기술 선택 근거, 윤리·안전 안내

이번 팀의 핵심 설명은 다음 한 문장으로 통일한다.

> 일기를 KcELECTRA로 6개 감정 대분류하고, LLM이 세부 감정을 제안한다. 사용자가 무드 미터에서 최종 감정을 확정하며, 기록은 Long-term Memory로 축적되고 검증된 자기돌봄 자료를 RAG로 검색해 맞춤 피드백을 만든다.

## 2. 4주 개발 순서

### 1주차: 화면과 데이터 계약

- 현재 프로토타입을 팀원 모두 사용해 본다.
- 필수 화면과 문구를 확정한다.
- `POST /api/emotions/analyze` 요청·응답 형식을 합의한다.
- 공개 모델 라이선스, 라벨 순서, 토크나이저, 최대 입력 길이를 모델 카드에서 확인한다.

완료 기준: 일기 10개를 넣었을 때 프론트 흐름을 막힘 없이 시연한다.

### 2주차: KcELECTRA API

- Python FastAPI 서버를 만든다.
- Hugging Face의 공개 KcELECTRA 감정 분류 모델을 로드한다.
- 모델 출력 라벨 ID를 `분노/기쁨/불안/당황/슬픔/상처`로 정확히 매핑한다.
- softmax 확률과 상위 3개 감정을 반환한다.
- 짧은 문장, 긴 문장, 빈 입력, 욕설·오탈자 포함 문장을 테스트한다.

요청 예시:

```json
{
  "text": "내일 발표 생각 때문에 계속 잠이 안 와요.",
  "self_reported_stress": 4
}
```

응답 예시:

```json
{
  "model": "kcelectra-korean-emotion",
  "labels": [
    { "name": "불안", "score": 0.71 },
    { "name": "슬픔", "score": 0.12 },
    { "name": "당황", "score": 0.08 }
  ],
  "disclaimer": "감정 분류 결과는 의료적 진단이 아닙니다."
}
```

완료 기준: 팀이 만든 검증 문장 100개에서 Accuracy와 Macro-F1을 기록하고, 응답 시간이 목표 범위 안에 든다.

### 3주차: Memory + RAG + LLM 코치

- Supabase에 사용자별 일기, AI 추정값, 사용자 최종값을 분리해 저장한다.
- 원문 전체를 장기 기억에 그대로 넣지 말고 날짜·감정·사건 요약을 저장한다.
- RAG에는 공공기관의 공개 자료와 팀이 직접 작성한 호흡·감정 정리 가이드만 넣는다.
- LLM 프롬프트에는 `감정 인정 → 상황 요약 → 작은 선택지 1~2개 → 진단 금지` 규칙을 둔다.
- 위기 표현이 감지되면 일반 코칭을 중단하고 즉각적인 전문 도움 안내를 제공한다.

완료 기준: 과거 기록이 있는 사용자와 없는 사용자에게 서로 다른 피드백이 생성되고, 답변 근거 자료를 확인할 수 있다.

### 4주차: 통합·테스트·배포

- 프론트와 API를 연결하고 오류·대기·빈 상태를 완성한다.
- 5명 이상이 3일 정도 사용하도록 테스트한다.
- 설문: 기록 난이도, 분석 공감도, 수정 기능 이해도, 추천 유용성, 재사용 의향.
- 사용자 수정률과 AI-사용자 일치율을 기록하되, 수정률이 높다고 사용자가 틀렸다고 해석하지 않는다.
- 피드백 중 영향이 큰 항목 2~3개를 실제 반영한다.

완료 기준: 배포 URL, 테스트 결과, 반영 전후 화면, 기술 선택 근거를 발표 자료에 포함한다.

## 3. 초보 팀 4명 역할 예시

| 역할 | 주요 업무 | 첫 작업 |
|---|---|---|
| PM/백엔드 | 일정, API, Supabase, 통합 | API 명세와 DB 표 작성 |
| AI/데이터 | KcELECTRA 검증, 지표, 모델 API | 모델 카드와 라벨 순서 확인 |
| 프론트엔드 | 화면, 상태, API 연결 | 현재 MVP에서 mock 함수를 fetch로 교체 |
| RAG/QA | 자료 수집, 청킹, 테스트, 안전 | 허용된 자료 목록과 테스트 문장 100개 작성 |

## 4. 데이터 구조

`emotion_entries`

- `id`, `user_id`, `created_at`
- `diary_text` 또는 암호화된 원문 참조
- `self_reported_stress`
- `model_name`, `model_version`
- `model_labels_json`
- `ai_detailed_mood`
- `user_final_mood`
- `user_corrected` boolean
- `memory_summary`

핵심은 AI가 고른 값과 사용자가 최종 선택한 값을 덮어쓰지 않고 둘 다 보관하는 것이다.

## 5. 모델 검증 체크리스트

- 모델 카드에서 학습 데이터와 라이선스를 확인했는가?
- 라벨 ID 순서를 코드에서 추측하지 않고 설정 파일에서 읽었는가?
- 공개 모델의 보고 점수를 우리 서비스 성능처럼 표현하지 않았는가?
- 우리 검증 세트의 Accuracy와 Macro-F1을 따로 계산했는가?
- 평온·피곤함처럼 6개 라벨 밖의 감정을 LLM과 사용자 선택으로 보완하는가?
- 일기 원문과 모델 결과를 로그에 무분별하게 남기지 않는가?

## 6. 발표에서 보여줄 90초 시연

1. 사용자가 발표 실패에 대한 일기를 쓴다.
2. KcELECTRA가 불안·슬픔·당황 확률을 보여준다.
3. LLM이 `걱정되는/초조한/지친`을 제안한다.
4. 사용자가 실제 감정은 `답답한`으로 수정한다.
5. Long-term Memory가 지난 발표 걱정 기록과 연결한다.
6. RAG 근거를 사용한 1분 호흡을 추천한다.
7. 기록 화면에서 AI 추정과 사용자 확정의 차이를 설명한다.

이 흐름이 분류 모델, Human-in-the-loop, Memory, RAG, 생성형 AI 코칭을 한 번에 보여준다.

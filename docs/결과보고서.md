## 1. 문제 정의

### 1.1 우리가 본 공백

감정 관리 서비스는 두 갈래로 나뉘어 있고, 그 사이가 비어 있습니다.

| 유형 | 하는 일 | 못 하는 일 |
|---|---|---|
| 기록형 앱 | 감정 이모지를 고르고 저장한다 | "그래서 지금 무엇을 해야 하는가"에 답하지 못한다 |
| 대화형 챗봇 | 그럴듯한 위로 문장을 만든다 | 근거가 없어 사용자가 신뢰 여부를 판단할 수 없다 |

### 1.2 우리가 정의한 문제

> **"오늘 내 감정이 무엇인지"에서 멈추지 않고, "그래서 지금 15분 동안 무엇을 하면 되는지"까지 출처와 함께 이어주는 서비스가 없다.**

이 문제를 풀려면 세 가지를 동시에 만족해야 했습니다.

| 요구 | 왜 어려운가 |
|---|---|
| 감정 판정이 **검증 가능**해야 한다 | LLM에게 감정을 물으면 그럴듯한 답은 나오지만 근거를 제시할 수 없다 |
| 추천에 **출처**가 있어야 한다 | 생성형 AI는 존재하지 않는 활동·효능을 만들어낼 수 있다 |
| 개인화하되 **개인정보를 최소로** 다뤄야 한다 | 감정 일기는 가장 민감한 개인 기록이다 |

### 1.3 범위 밖으로 명시한 것

의료적 진단·치료·처방, 위기 상담 대체, 일기 원문의 서버 저장 및 학습 이용 — 세 가지는 명시적으로 하지 않습니다.

## 2. 해결 설계

### 2.1 전체 구조

![시스템 아키텍처](architecture.svg)

```
일기 입력 → [Agent] 의도 판별
              ├─ analyze_emotion    → KcELECTRA 실제 추론 → 감정 점수
              ├─ retrieve_grounding → 출처 카드 검색 (RAG)
              ├─ generate_coach_message → 생성형 AI, 출처 안에서만 문장 생성
              └─ recommend_healing  → 출처 링크가 붙은 활동 카드
           → 사용자가 무드 미터에서 최종 감정 확정
           → (동의 시) 선호 활동 30일 기억
```

### 2.2 필수 기술 요소 — 요구 2개, 구현 4개

| 요소 | 구현 위치 | 핵심 내용 | 검증 |
|---|---|---|---|
| **AI Agent** | `coach_agent.py` | 일기/대화/휴식요청 의도를 판별해 필요한 도구만 순서대로 호출. 실행 추적에 도구 이름만 기록 | `test_agent.py`<br>`evidence/agent-check.json` |
| **RAG** | `rag.py`<br>`healing_knowledge.py` | 감정·스트레스·가용 시간으로 활동 카드를 검색하고 출처·라이선스를 함께 반환 | `test_rag.py`<br>`evidence/rag-check.json` |
| **생성형 AI** | `llm.py` | 코디세이 제공 API(OpenAI 호환)에 **출처 카드만** 전달해 코치 문장 생성. 일기 원문 미전송, 실패 시 자동 폴백 | `test_llm.py`<br>`evidence/llm-check.json` |
| **Long-term Memory** | `memory_db.py` | 동의 기반 선호 활동 저장, 30일 자동 만료, 사용자 삭제 | `test_memory_restart.py`<br>`evidence/memory-retention-check.json` |

### 2.3 기술적 의사결정과 근거

평가에서 가장 중요한 부분이라 판단해 **선택하지 않은 대안과 그 이유**를 함께 적습니다.

| # | 결정 | 검토한 대안 | 선택 근거 |
|---|---|---|---|
| 1 | 감정 분류에 **전용 모델(KcELECTRA)** 사용 | LLM에게 감정 추정을 요청 | LLM 추정은 근거를 제시할 수 없다. 분류 모델은 **점수와 모델 버전을 공개**할 수 있어 제3자가 재현·검증할 수 있다 |
| 2 | 생성형 AI를 **문장 작성에만** 사용 | 분석부터 추천까지 LLM에 일임 | 판정은 검증 가능해야 하고 문장은 자연스러워야 한다. **역할을 분리**해 각 층의 강점만 쓴다 |
| 3 | LLM에 **일기 원문을 보내지 않음** | 원문을 그대로 전달해 공감도 향상 | 감정 일기는 가장 민감한 기록이다. 감정 라벨·스트레스·출처 카드만으로도 충분한 품질을 확인했고, 유출 경로 자체를 제거하는 편이 낫다고 판단 |
| 4 | 생성 실패 시 **결정론적 폴백** | 오류 화면 표시 | 외부 API 장애가 서비스 중단이 되어서는 안 된다. 폴백 여부는 `generation` 필드로 **항상 공개**한다 |
| 5 | 일기 원문 **브라우저 보관** | 서버 DB 저장 | 서버 유출 위험 자체를 제거. 개인정보 최소 수집 원칙 |
| 6 | 선호 기억 **30일 만료** | 무기한 보관 | 개인화와 보호를 동시에 증명. 만료·삭제를 테스트로 검증 |
| 7 | 배포에 **Hugging Face Spaces** | Render 유료 플랜 | 모델이 HF에 있어 캐시가 빠르고, 무료 등급으로 **영구 HTTPS URL** 확보. 모델을 이미지에 포함해 콜드스타트 제거 |
| 8 | 프론트엔드 **순수 HTML/JS** | React 등 프레임워크 | 빌드 체인 없이 정적 배포, 팀 전원이 직접 수정 가능 |

## 3. 생성형 AI 통합 상세

### 3.1 접지(grounding) 방식

생성형 AI가 자유롭게 답하면 존재하지 않는 활동이나 의료적 조언을 만들어낼 수 있습니다. 이를 **세 겹으로** 막았습니다.

| 층 | 방법 |
|---|---|
| 입력 제한 | 프롬프트에 검색된 출처 카드 3장만 넣는다. 일기 원문은 넣지 않는다 |
| 지시 제한 | "카드에 없는 활동을 만들지 않는다 / 진단·처방·병원 권유 금지 / 감정 단정 금지 / 2~3문장" |
| 출력 검사 | 생성 문장에 금지어(진단·처방·치료·우울증 등)가 있으면 **폐기하고 규칙 기반으로 폴백** |

### 3.2 응답 경로 공개

모든 응답은 어느 경로로 만들어졌는지 스스로 밝힙니다.

| `generation` 값 | 의미 | 사용자 화면 표시 |
|---|---|---|
| `llm_grounded` | 생성형 AI가 출처 안에서 작성 | "AI가 생성한 문장이며 의료적 진단이 아니에요" |
| `deterministic_fallback` | 규칙 기반 문장 | "코치 문장은 규칙 기반이에요" |

폴백 사유(`not_configured` / `call_failed` / `safety_filter`)도 응답에 포함되어 운영 중 진단이 가능합니다.

### 3.3 실제 동작 예

**입력**: `내일 발표를 잘할 수 있을지 걱정돼요.` (스트레스 3)

| 단계 | 결과 |
|---|---|
| `analyze_emotion` | **불안 0.941** (실측, `evidence/api-check.json`) · 모델 리비전 `2eaf89d8` 고정 |
| `retrieve_grounding` | 1분 호흡하기(NHS) · 주변 감각 돌아보기(Kent NHS) · 10분 짧은 필사(Gutenberg) |
| `generate_coach_message` | 위 3장만 컨텍스트로 전달 → 2~3문장 생성 |
| 최종 응답 | 코치 문장 + 출처 카드 3장 + `generation: llm_grounded` + 도구 실행 추적 |

## 4. AI 윤리 및 개인정보

### 4.1 데이터 처리

| 데이터 | 저장 위치 | 보존 | 동의 | 외부 전송 |
|---|---|---|---|---|
| 일기 원문 | 브라우저 localStorage | 사용자 삭제 시까지 | 불필요 | **없음** (LLM에도 미전송) |
| 확정 감정·스트레스 | 브라우저 localStorage | 동일 | 불필요 | 없음 |
| 선호 활동 | 서버 SQLite | **30일 자동 삭제** | **필수** | 없음 |
| 만족도·의견 | 서버 SQLite (익명) | 과제 종료 시 파기 | **필수** | 없음 |

### 4.2 지킨 원칙

- AI가 생성·추천한 콘텐츠임을 **화면에 표시**합니다.
- 동의를 거부해도 **핵심 기능을 그대로** 사용할 수 있습니다.
- 감정 분류 점수를 **진단이나 감정 구성비로 표시하지 않습니다**. 최종 감정은 사용자가 확정합니다.
- Agent 실행 추적에 **도구 이름만** 남기고 일기 원문을 넣지 않습니다.
- 필사·음악 콘텐츠는 **저작권 만료 또는 공개 라이선스** 자료만 사용하고 긴 원문을 저장하지 않습니다.

### 5.3 모델 적용 결과

전체 내용은 [모델 적용 결과](모델적용결과.md)에 정리했으며, 핵심만 옮깁니다. **모든 수치는 실측값**입니다.

#### 실제 분류 결과 (`evidence/api-check.json`)

| 입력 | HTTP | 최상위 감정 | 점수 | 청크 |
|---|---|---|---|---|
| 걱정 문장 (`내일 발표를…`) | 200 | **불안** | **0.941** | 1 |
| 긴 글 (128토큰 초과) | 200 | 불안 | 0.437 | **2** |
| 빈 입력 / 범위 밖 스트레스 | 422 | — | — | 입력 검증 차단 |

긴 글에서 점수가 낮아진 것은 오작동이 아니라, 청크별 결과를 토큰 수로 가중 평균해 **단일 감정으로 단정하지 않는** 의도된 동작입니다.

#### 추가 학습 시도와 채택하지 않은 이유

`team_motion` 발화 **847,156건**(파일 2,335개)으로 추가 학습을 시험했습니다.

| 문제 | 수치 |
|---|---|
| `상처` 라벨 신규 표본 없음 | 6종 중 1종 누락 → 기존 분류 능력 손상 위험 |
| 극심한 클래스 불균형 | 학습셋 기쁨 330,711 vs 불안 16,233 (**약 20:1**) |
| 제외된 라벨 | 없음 206,219 · 사랑스러움 34,624 (대응 라벨 없음) |

CPU 환경 제약으로 학습 100 / 검증 100 / 테스트 100건, 1에폭 파일럿으로 진행한 결과:

| 구분 | Loss | Accuracy | Macro F1 |
|---|---|---|---|
| 검증 | 1.9917 | 0.24 | 0.2395 |
| **테스트** | **1.8622** | **0.26** | **0.2496** |

5개 클래스 무작위 추측의 기대 정확도가 0.20인데 측정값이 0.26입니다. **무작위보다 의미 있게 낫다고 말할 수 없는 수준**이므로, 서비스에는 **공개 모델을 그대로 적용**했습니다.

> 이 수치는 데이터가 쓸모없다는 뜻이 아니라 **CPU·100건·1에폭 조건에서는 개선을 확인할 수 없었다**는 뜻입니다. 실패한 시도를 지우지 않고 남긴 것도 기록의 일부입니다.

| 현재 한계 | 영향 | 다음 단계 |
|---|---|---|

## 9. 결론

이 프로젝트에서 팀이 가장 신경 쓴 것은 **"AI를 얼마나 많이 썼는가"가 아니라 "어디에 어떤 AI를 썼고 왜 그렇게 나눴는가"** 였습니다.

- 감정 **판정**은 검증 가능해야 하므로 전용 분류 모델에 맡기고, 점수와 모델 버전을 공개했습니다.
- 감정 **표현**은 자연스러워야 하므로 생성형 AI에 맡기되, 검색된 출처 안에서만 말하도록 세 겹으로 제한했습니다.
- **개인정보**는 가장 민감한 부분이므로, 일기 원문이 서버에도 생성형 AI에도 가지 않는 경로를 설계했습니다.

구현하지 못한 것을 구현한 것처럼 적지 않는 것 역시 이 보고서의 원칙입니다. 체크 표시는 실제로 확인한 항목에만 붙였습니다.

## 2. 문제 정의

### 2.1 관찰한 문제

감정 관리 앱은 많지만 대부분 두 갈래로 나뉜다.

1. **기록만 하는 앱** — 사용자가 감정 이모지를 고르고 끝난다. 기록이 쌓여도 "그래서 지금 뭘 해야 하는가"에 답하지 못한다.
2. **대화만 하는 챗봇** — 위로 문장은 잘 만들지만, 근거 없이 생성된 문장이라 사용자가 "이게 나한테 맞는 말인가"를 판단할 수 없다. 의료적 조언처럼 읽히는 위험도 있다.

### 2.2 해결하려는 지점

> **"오늘 내 감정이 무엇인지"에서 멈추지 않고, "그래서 지금 15분 동안 무엇을 하면 되는지"까지 출처와 함께 이어주는 서비스**

세 가지를 동시에 만족시키는 것이 이 프로젝트의 과제다.

| 요구 | 설계 대응 |
|---|---|
| 감정 판정이 그럴듯한 생성 문장이 아니라 **검증 가능한 결과**여야 한다 | 공개 KcELECTRA 한국어 감정 분류 모델을 실제 추론으로 사용, 모델 버전 고정 |
| 추천 활동이 **출처 있는 콘텐츠**여야 한다 | RAG로 힐링 지식 카드를 검색하고 응답에 출처 링크를 붙임 |
| 개인화하되 **개인정보를 최소로** 다뤄야 한다 | 일기 원문은 서버에 저장하지 않음(브라우저 보관), 선호 활동만 동의 후 30일 한시 저장 |

### 2.3 하지 않는 것 (범위 밖 명시)

- 의료적 진단·치료·처방을 제공하지 않는다.
- 위기 상황(자해·자살 등) 상담을 대체하지 않으며, 해당 신호는 안전 문구로 분기한다.
- 사용자의 일기 원문을 서버에 저장하거나 학습에 사용하지 않는다.

## 3. 타겟 사용자

### 3.1 주 사용자 (Primary)

**20~40대 직장인·학생 중 "상담까지는 아니지만 감정을 정리할 곳이 필요한" 사람**

- 하루에 5~10분, 주로 밤에 휴대폰으로 접속한다.
- 감정을 글로 쓰는 데는 익숙하지만, 그 다음에 무엇을 해야 할지는 모른다.
- 병원·상담센터는 심리적·비용적 문턱이 높다고 느낀다.

### 3.2 페르소나

| 항목 | 내용 |
|---|---|
| 이름 | 김서연 (29, 사무직) |
| 상황 | 발표 전날 밤, 잠이 오지 않아 휴대폰을 켠다 |
| 입력 | "내일 발표를 잘할 수 있을지 걱정돼요." 스트레스 3점 |
| 기대 | 내 감정에 이름을 붙여주고, 지금 당장 할 수 있는 짧은 행동 하나를 알려주는 것 |
| 이탈 조건 | 로그인 요구 / 응답 5초 초과 / "병원에 가보세요" 같은 무성의한 답변 |

### 3.3 사용자 여정

```
접속 → 오늘의 일기 작성 → 감정 태그·스트레스 선택 → AI 분석 요청
  → 모델 감정 후보 확인 → 무드 미터에서 내 감정으로 직접 수정
  → 저작권 만료 인용구·추천 꽃과 향으로 마음 한 번 더 살피기
  → 출처 있는 힐링 활동 추천(호흡·감각·자연의 소리·필사·음악·꽃·취미)
  → 링크로 나가지 않고 앱 안에서 5단계 안내대로 수행
  → 만족도 1~5점 응답 → (동의 시) 선호 활동 기억 → 다음 방문 시 반영
  → 기록이 쌓이면 주·월·연 흐름 그래프와 기간별 감정 분석 보고서
```

## 4. AI 활용 방식

### 4.1 왜 이 구조인가

| 설계 결정 | 이유 |
|---|---|
| 감정 분류를 LLM이 아닌 **전용 분류 모델**로 | LLM 감정 추정은 근거를 제시할 수 없다. 분류 모델은 점수와 모델 버전을 공개할 수 있어 검증 가능하다. |
| 코치 응답을 **Agent 도구 호출**로 | 일기/대화 의도를 구분해 필요한 도구만 순서대로 실행한다. 실행 추적에 도구 이름만 남겨 원문 유출을 막는다. |
| 문장 생성을 **생성형 AI**에 맡기되 출처로 접지 | 자연스러운 공감 문장은 생성형이 우위다. 다만 검색된 출처 카드 밖으로 나가지 못하게 제한한다. |
| 생성형 AI에 **일기 원문을 보내지 않음** | 감정 라벨·스트레스·출처 카드만으로 충분한 품질을 확인했다. 유출 경로 자체를 없앤다. |
| 추천 문장에 **RAG 근거**를 결합 | "왜 이걸 추천했는가"를 출처 카드로 답할 수 있다. |
| 기억을 **동의·기한 기반**으로 | 개인화와 개인정보 보호를 동시에 증명한다. |

### 4.2 필수 기술 요소 충족 (과제 요구: 2개 이상)

| 기술 요소 | 구현 위치 | 검증 증거 |
|---|---|---|
| **AI Agent** | `coach_agent.py` — 의도 판별 후 `analyze_emotion` → `recommend_healing` 순차 호출 | `test_agent.py`, `evidence/agent-check.json` |
| **RAG** | `rag.py` + `healing_knowledge.py` — 감정별 힐링 지식 검색, 출처 링크 부착 | `test_rag.py`, `evidence/rag-check.json` |
| **생성형 AI** | `llm.py` — 출처 카드만 컨텍스트로 받아 코치 문장 생성, 안전 검사·자동 폴백 | `test_llm.py`, `evidence/llm-check.json` |
| **Long-term Memory** | `memory_db.py` — 동의 기반 선호 활동 저장, 30일 만료·삭제 | `test_memory_restart.py`, `evidence/memory-retention-check.json` |

→ **4개 충족** (요구는 2개 이상)

### 4.3 Agent 도구 계약

| 도구 | 입력 | 출력 | 실패 시 |
|---|---|---|---|
| `analyze_emotion` | 일기 텍스트, 스트레스 1~5 | 6개 감정 점수 + 무드 미터 좌표 | 입력 오류 안내, 원문 보존 |
| `retrieve_grounding` | 감정 좌표, 질의 | 출처가 있는 지식 카드 목록 | 검색 결과 없음을 그대로 표시 |
| `generate_coach_message` | 감정 라벨, 스트레스, 출처 카드 3장 | 2~3문장 코치 문장 (출처 접지) | 규칙 기반 문장으로 자동 폴백, 사유 공개 |
| `recommend_healing` | 감정 좌표, 시간, 선호 | 출처 링크가 붙은 추천 카드 | 위치 권한 없으면 비위치 추천 |
| `save_user_feedback` | 만족도 1~5, 선택 의견, 동의 | 익명 집계 저장 | 동의 없으면 저장하지 않음 |

### 4.4 생성형 AI의 안전 설계

생성형 AI가 자유롭게 답하면 존재하지 않는 활동이나 의료적 조언을 만들어낼 수 있다. 세 겹으로 제한했다.

| 층 | 방법 |
|---|---|
| 입력 제한 | 프롬프트에 검색된 출처 카드 3장만 넣는다. **일기 원문은 넣지 않는다** |
| 지시 제한 | 카드에 없는 활동 생성 금지 / 진단·처방·병원 권유 금지 / 감정 단정 금지 / 2~3문장 |
| 출력 검사 | 금지어가 검출되면 생성 문장을 **폐기하고 규칙 기반으로 폴백** |

모든 응답은 `generation` 필드로 경로를 공개한다.

| 값 | 의미 |
|---|---|
| `llm_grounded` | 생성형 AI가 출처 안에서 작성 |
| `deterministic_fallback` | 규칙 기반 문장 (사유: `not_configured` / `call_failed` / `safety_filter`) |

## 5. 기술적 접근 방식

### 5.1 기술 스택과 선정 이유

| 영역 | 선택 | 선정 이유 |
|---|---|---|
| 감정 분류 | `GGARA02/kcelectra-korean-emotion` (버전 `2eaf89d8…` 고정) | 한국어 구어체 감정 분류에 특화. 버전 고정으로 재현 가능 |
| 생성형 AI | **코디세이 제공 API** (OpenAI 호환) | 과정에서 제공하는 자원을 사용해 비용·키 관리 부담이 없다. OpenAI 호환 규격이라 공급자 교체가 환경변수 세 개로 끝난다 |
| 백엔드 | FastAPI + Uvicorn | 비동기 처리, 자동 문서화, 모델 추론 서버로 가볍다 |
| 프론트엔드 | 순수 HTML/CSS/JS (`dist/`) | 빌드 체인 없이 정적 배포 가능, 팀 전원이 수정할 수 있다 |
| 저장소 | 브라우저 localStorage + 서버 SQLite | 일기 원문은 사용자 기기에, 익명 집계만 서버에. 개인정보 최소 수집 원칙 |
| 배포 | Docker → Hugging Face Spaces (CPU basic) | 모델이 HF에 있어 캐시가 빠르고, 무료 등급으로 영구 HTTPS URL 확보. 모델을 이미지에 동봉해 콜드스타트 제거 |
| 형상관리 | Git / GitHub | 커밋 단위로 기능·문서 이력 추적 |

### 5.2 데이터 처리 원칙

| 데이터 | 저장 위치 | 보존 기간 | 동의 |
|---|---|---|---|
| 일기 원문 | 브라우저 localStorage | 사용자가 삭제할 때까지 | 불필요(서버 미전송 저장) |
| 확정 감정·스트레스 | 브라우저 localStorage | 동일 | 불필요 |
| 선호 활동 | 서버 SQLite | **30일** 후 자동 정리 | **필수** |
| 만족도 점수·의견 | 서버 SQLite (익명) | 과제 종료 시 파기 | **필수** |

생성형 AI에 전달되는 것은 **감정 라벨 · 스트레스 숫자 · 출처 카드 3장**뿐이며, 일기 원문은 전송하지 않는다.

### 5.3 비기능 요구사항

| ID | 항목 | 목표 |
|---|---|---|
| NFR-01 | 응답 속도 | 감정 분석 5초 이내 (모델 최초 로딩 제외, 로딩 안내 표시) |
| NFR-02 | 접근성 | 큰 글자, 터치 영역 확보, 색+텍스트 병기, 모션 줄이기 지원 |
| NFR-03 | 개인정보 | 일기 원문 서버 미저장, 동의 없는 저장 없음, 삭제 동선 제공 |
| NFR-04 | 투명성 | 모델 버전·출처·AI 생성 여부와 생성 경로(`generation`)를 화면과 응답에 명시 |
| NFR-05 | 가용성 | 헬스체크 엔드포인트 제공, 모델 미로딩 시 점검 모드 폴백 |

### 5.4 AI 윤리 준수

- 모든 AI 생성·추천 콘텐츠에 **AI가 만든 내용임을 화면에 표시**한다.
- 개인정보 수집 전 **동의 화면**을 거치며, 거부해도 핵심 기능을 사용할 수 있다.
- 감정 분류 점수를 **진단이나 감정 구성비로 표시하지 않는다**. 최종 감정은 사용자가 직접 확정한다.
- 필사·음악 콘텐츠는 **저작권 만료 또는 공개 라이선스** 자료만 사용하고 긴 원문은 저장하지 않는다.

## 8. 성공 기준

프로젝트 완료를 판단하는 기준은 다음과 같다.

- [ ] 외부에서 접근 가능한 HTTPS URL에서 휴대폰으로 감정 분석이 성공한다.
- [ ] 서로 다른 실사용자 5명 이상이 핵심 흐름(일기 → 분석 → 추천 → 만족도)을 완료한다.
- [ ] 사용자 피드백으로 최소 1건 이상을 수정하고, 개선 전/후를 기록한다.
- [ ] Agent·RAG·생성형 AI·Long-term Memory 4요소의 동작을 증거 파일로 제시한다.
- [ ] 모든 소스와 문서가 GitHub `main`에 반영되고 최종 커밋 해시를 제출한다.
- [ ] 발표에서 문제 정의 → AI 활용 근거 → 사용자 피드백 반영을 10분 안에 설명한다.
